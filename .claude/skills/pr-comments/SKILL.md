PRの未解決レビューコメントに対応し、再レビューを依頼するまでを**1周だけ**実行する。

## やること

1. 対象PRを特定する（`$ARGUMENTS` のPR番号、なければ現在のブランチから）
2. 未解決の指摘を集める。インラインコメント・レビュー総評・PR全体コメントの**3種すべて**見る（総評の重要な指摘を取りこぼすため）。解決済みスレッドは触らない。REST には `isResolved` が無いので GraphQL の `reviewThreads` を使う。
3. 各指摘を評価して対応する。ユーザーの承認は待たず自分で判断する。
   - 妥当 → 直す
   - 同意できない → 直さず、理由を**該当スレッドへの返信で**返す（黙って無視すると放置と区別がつかない）
   - 何を求められているか曖昧 → 推測で直さず、質問を返してスキップ
4. commit（メッセージは `git log` で既存慣習に合わせる）→ push → `/code-review` とコメントして再レビュー依頼
5. 対応内容・返信で返した指摘・質問でスキップした指摘・push と再レビュー依頼の結果を報告して止まる

自動レビューbotのコメントも人間の指摘と同じ基準で評価する（bot だからと無条件に従わない）。

## この環境固有の注意

- **push は HTTPS + gh 経由**。SSHの22番ポートが塞がれているため SSH remote への push は失敗する:
  `git -c credential.helper='!gh auth git-credential' push https://github.com/{owner}/{repo}.git HEAD:{branch}`
- **返信本文は Write ツールでファイルに書いて** `--body-file` などで渡す。heredoc は noclobber 下で黙って失敗する。
- **PRがdraftだと自動 code-review は走らない**。draft のときはその事実をユーザーに伝える（自分で ready for review にしない）。

## やらないこと

- 2周目を自動で回さない（bot同士の往復でコミットが積み上がる）
- スレッドを自分でresolveしない（解決判断はレビュアーの仕事）
- 返信本文に `/code-review` 以外のスラッシュコマンド文字列を書かない（他のbotを誤起動しうる）
- PRが見つからないときにPRを新規作成しない。止まってユーザーに伝える
- push が失敗したら再レビューを依頼しない
